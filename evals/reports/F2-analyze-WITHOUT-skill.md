# Shiftboard - UI/UX audit (control run, no skill)

Target: `<tests>\fixture2-shiftboard-react` (React 18 + Tailwind Play CDN, hash router, 4 routes).
Method: full read of every source file, plus headless-Chrome renders at 1440px and 390px (screenshots in `round5/shots-f2-noskill/`: `schedule.png`, `team.png`, `shift-8.png`, `settings.png`, `schedule-mobile.png`). Contrast ratios computed with the WCAG 2.x relative-luminance formula from the Tailwind default hex values. Read-only; nothing in the fixture was changed. Server on port 8139 was stopped afterwards.

Paths below are relative to the fixture root. Severity: Critical = blocks a core task, causes data loss, or locks out a class of users; Major = significant friction, confusion or WCAG AA failure; Minor = polish/consistency.

Summary: 79 findings - 11 Critical, 48 Major, 20 Minor.

## 2. Top 5 fixes (highest user impact per unit effort)

1. **Make the shift form usable and safe** (C1-C8, C14): remove the hard-coded error banner; add visible labels for every field; use time inputs instead of `HH:MM:SS` text; cut required fields to who/role/start/end with defaults for the rest; per-field error messages; add a confirmation or undo to "Delete" and demote it. This is the app's core task and currently its worst screen.
2. **Fix keyboard/screen-reader access to core controls** (A2, A9, A15, B13, E4, A8): real `<a>` links in a `<nav>`, a `role="switch"` button for Toggle, links for open-slot rows, `aria-label`s on icon buttons, and replace every bare `outline-none` with a `focus-visible` ring; add `<main>`/`<h1>` per screen.
3. **Restore contrast and hierarchy on the Schedule screen** (B1, B3, B4, B8, B9, F1, A17): delete the welcome paragraph; one H1 + week switcher; make "Publish week" the single primary button; re-do the KPI strip with readable text and promote Unfilled + Projected overtime into it; drop global `font-light`; nothing lighter than `ink-500` for text.
4. **One component system built on the tokens that already exist** (A18, B5, B15, D2, E8): a single Button (primary/secondary/tertiary/destructive, one radius), Card (`rounded-card shadow-card`), Input and label pattern, 4px spacing scale - replacing the four button shapes/colors, the mismatched shadows and the arbitrary pixel values. The Danger zone, the Team search/empty state and `WeekGrid` are the reference implementation.
5. **Plain, consistent language and honest feedback** (A3, A4, B11, E1-E3, B17, C2): rename nav to Schedule/Team/Settings with a clear active state and matching page titles; use "shift"/"schedule" everywhere; label the Settings fields, accept human phone formats, rename "OK" to "Save changes" with a visible saved confirmation; replace "No data"/"Invalid input."/"Error: invalid value." with specific, actionable messages.

Next in line: responsive layout (A1) and removing dead/promo controls from the top bar (A6, A8, A11, B6).

## 3. What the app does well

- **Week grid** (`src/components/WeekGrid.jsx`): shifts are real `<a href>` links with `focus-visible` rings and hover states; uses the `brand`/`ink`/`surface`/`rounded-card` tokens; open shifts are distinguished by dashed amber border **plus** the text "Open - unassigned" (not color alone); today's column is marked with both tint and the word "Today"; times use `tabular-nums`; shifts are sorted by start time. Contrast passes (ink-500 on amber-50 4.66:1, brand-700 on brand-50 5.82:1).
- **Danger zone** (`src/screens/Settings.jsx:99-151`): semantic `<section aria-labelledby>` + `<h2>`, plain-language consequences and reversibility ("restore within 30 days"), progressive disclosure, type-the-name confirmation with a proper `<label htmlFor>`, destructive button disabled until the name matches, specific button labels ("Archive Harbour St" / "Keep location"), ellipsis on the opener, visible focus rings, visually quiet until needed.
- **Team search** (`src/screens/Team.jsx:21-33`): visible label, `type="search"`, helpful placeholder that is not the only label, focus ring, instant filtering on name or role.
- **Time-off empty state** (`src/screens/Team.jsx:105-117`): says what is empty, why it matters, and offers the next action with a clear verb-led button.
- A coherent token set (brand/ink/surface/danger/ok, card radius, two shadows) is already defined (`index.html:9-54`); it only needs to be used.
- `lang="en"` and viewport meta present; hash routes are deep-linkable; `ShiftDetail` is keyed by id so state resets between shifts; route change scrolls to top; radio inputs are wrapped in labels; "Assign to" and "Role" selects have proper `<label htmlFor>`.

## 4. What I could not verify

- **Interactive behaviour in a real browser**: I rendered static headless screenshots only (no clicking/typing). Focus order, the actual look of browser-default focus where `outline-none` is set, hover states, the toggle animation, the archive confirm flow and the post-submit redirect were assessed from code, not observed.
- **Screen-reader output** (NVDA/JAWS/VoiceOver) was not tested; accessibility findings are from markup analysis.
- **Contrast figures** are computed from Tailwind's default palette hex values and the theme in `index.html`; they assume the default Tailwind v3 palette served by the Play CDN and do not account for the additional thinning effect of `font-light`, anti-aliasing, or semi-transparent compositing beyond the two `white/50`/`white/60` cases I blended manually.
- **Table overflow at 1240px (D3)** is arithmetic (82% of 1240 minus padding = ~973px < 1100px), not a measured render; at 1440px the Team screenshot confirms the table just fits. Team and Settings screenshots were reviewed and match the code-based findings (36 solid row buttons, unlabeled pre-filled Settings fields, "OK" button, centered gray paragraph).
- **Intermediate breakpoints** (768/1024px), zoom at 200%/400%, Windows high-contrast mode, dark mode (a moon icon exists but does nothing) and `prefers-reduced-motion` were not rendered.
- **Performance** (time to first render with in-browser Babel) was not measured.
- **Real user intent**: whether fields such as cost center, approving manager and reason are genuine compliance requirements is unknown; if they are, C6 becomes "default and pre-fill them" rather than "remove them".
- No usability testing with actual cafe managers; severity ratings are expert judgement.
